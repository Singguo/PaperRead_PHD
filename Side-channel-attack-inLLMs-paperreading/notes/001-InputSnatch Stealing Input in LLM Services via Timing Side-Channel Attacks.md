**摘要**：  
大语言模型（LLMs）具备广泛的知识和问答能力，已被部署于金融、医疗咨询等隐私敏感领域。在LLM推理过程中，为提升效率，业界普遍采用缓存共享机制（如前缀缓存和语义缓存），通过复用相同或相似请求的缓存状态或响应来加速服务。然而，本文指出这些缓存机制存在泄露用户私有输入的风险——缓存命中会导致可观测的响应时间变化，从而构成强有力的时序侧信道攻击线索。

为此，我们提出了 **InputSnatch**，一种新型基于时序的侧信道攻击方法，用于在LLM推理中窃取用户输入。该攻击面临在巨大搜索空间中构造候选输入以命中缓存的挑战。为解决此问题，我们设计了两个核心组件：（1）**输入构造器**，结合机器学习与大语言模型技术学习词汇关联，并采用优化搜索策略进行泛化输入构造；（2）**时间分析器**，通过统计拟合与时序异常剔除识别缓存命中模式，并持续反馈以优化构造策略。

我们在两种主流缓存机制上进行了实验，结果表明该方法在多种应用场景下均能取得高攻击成功率。例如，在采用静态提示工程的医疗问答系统中，可实现62%的精确疾病输入窃取率和13.5%的症状描述窃取率；在采用检索增强生成（RAG）的法律咨询系统中，语义级内容提取成功率高达43%至100%。本工作揭示了性能优化所带来的安全漏洞，强调在提升LLM推理效率的同时，必须优先考虑隐私与安全。

### 1. 核心矛盾

**论文试图解决的问题是：如何在真实、受限的黑盒API环境下，高效且精确地窃取大语言模型（LLM）服务中其他用户的私有输入（如医疗记录、法律咨询内容）。**

现有针对LLM的提示（prompt）窃取攻击存在三大关键缺陷：
- **无法精确恢复**：多数方法仅能恢复语义近似的内容，难以还原用户输入的原始措辞或关键细节；
- **场景泛化能力差**：攻击策略往往针对特定任务或模型定制，难以迁移到其他应用（如从客服系统迁移到医疗诊断）；
- **依赖不切实际的假设**：例如要求白盒访问模型内部状态、获取完整的token概率分布，或允许无限制地发起查询——这些在主流商业API（如OpenAI、Anthropic）中均不可行。

与此同时，工业界为提升LLM服务的吞吐量与响应速度，普遍部署了**缓存共享机制**（如前缀缓存 Prefix Caching 和语义缓存 Semantic Caching）。这类优化本应是“透明”的性能增强手段，但作者发现：**当不同用户的请求命中同一缓存时，推理延迟（特别是首Token生成时间 TTFT）会显著缩短**。这一**可观测的时序差异**，恰好构成了一个天然、稳定且无需特殊权限即可利用的**侧信道**。

因此，本文的核心洞见在于：**性能优化本身即漏洞源头**。当前SOTA攻击之所以失效，是因为它们将LLM视为孤立的模型，而忽略了其在真实云环境中与**系统级基础设施**（如KV Cache调度、共享内存）的深度耦合。InputSnatch 正是通过“自下而上”地建模这一**系统-算法协同引入的时序信号**，属于对现有攻击范式的“从1到N”的优化。

### 2. 学术谱系

#### **父节点（理论与方法继承）**
InputSnatch 的思想根源可追溯至三个关键研究脉络：

1. **传统缓存侧信道攻击**（如 Flush+Reload、Prime+Probe）  
   这类源自系统安全领域的经典技术（如文献 [44, 122, 135] 所示）证明：共享硬件资源（如CPU缓存）会因不同进程的访问模式产生可观测的时序差异，从而泄露敏感信息。InputSnatch 借鉴了这一“**通过共享资源竞争观测时序信号**”的核心范式，但将其从底层硬件（如LLC缓存）迁移至**高层AI推理栈中的KV缓存机制**，实现了对大模型服务的新型侧信道建模。

2. **成员推断攻击**（Membership Inference Attacks, MIA）  
   MIA（如 [13, 71, 72]）旨在判断某条数据是否属于模型的训练集，其核心假设是“模型对训练样本的响应行为存在统计偏差”。InputSnatch 虽不直接判断成员关系，但继承了“**利用模型行为差异反推输入属性**”的逻辑，并将关注点从“训练数据”转向“推理时的私有提示”。

3. **提示逆向工程**（Prompt Inversion / Leakage）  
   此前工作尝试从模型输出反推输入，例如：
   - 通过嵌入向量逆向重构提示（如 [16, 59, 105]）；
   - 利用响应语义或token长度序列推测原始问题（如 [67, 129, 138]）；
   - 通过分析next-token概率分布恢复输入（如 [78]）。  
   这些方法构成了InputSnatch在“**目标**（窃取提示）”上的直接先驱。

#### **竞争节点（同期/替代方案）**
论文明确对比并超越了以下依赖**高维输出特征**的提示恢复方法：
- **[67], [101], [138]**：基于响应内容进行语义对齐，仅能实现模糊的语义级恢复；
- **[16], [105]**：需白盒访问嵌入层或梯度，实用性受限；
- **[78]**：要求获取全词表的token概率分布，这在商业API中通常不可行。

这些方法共同的局限在于：**将LLM视为一个封闭的函数映射器**，忽视了其部署环境中的**系统级优化行为**。

#### **优化与颠覆性创新**
InputSnatch 的突破在于**视角转换**与**信号降维**：
- **视角上**：不再从模型输出（响应文本、概率、嵌入）入手，而是聚焦于**推理基础设施的行为**——即缓存命中与否所导致的**首Token生成时间**（TTFT）。
- **信号上**：将攻击依据从**高维、连续、噪声大的输出空间**（如概率分布、语义向量），简化为**低维、离散、强信号的二元状态**（缓存命中 vs. 未命中），并通过统计建模从噪声中提取该信号。
- **实用性上**：仅需标准API调用权限和时间测量能力，完全兼容现有黑盒服务约束。

#### **学术贡献定位**
由此，该工作**首次将系统安全中的缓存侧信道思想与AI隐私中的提示泄露问题深度耦合**，不仅揭示了工业级LLM推理引擎（如vLLM、TGI）中性能优化引入的新攻击面，更开创了“**LLM推理基础设施安全**”（LLM Inference Infrastructure Security）这一新兴交叉子领域，为后续研究提供了新的分析维度与防御靶点。

### 3. 核心思想与创新点

InputSnatch 的核心创新并非依赖复杂的模型逆向或高维信号分析，而是**从系统实现细节中挖掘可利用的时序规律**，并通过“**构造-反馈**”闭环实现高效攻击。其关键洞察与方法论可归纳为以下三点：

---

#### **(1) 反直觉的关键洞察：噪声中的强信号**

作者发现，尽管**首Token生成时间**（TTFT）受网络延迟、调度抖动等噪声干扰，看似不可靠，但**缓存命中带来的计算跳过效应**（如跳过部分Attention计算）会在TTFT上产生**系统性、可重复且幅度显著的时间节省**。  
更重要的是，主流推理引擎（如 vLLM）采用**块级**（block-level）管理KV缓存（例如每块16或128个token）。这意味着：
- 缓存命中是以**整块为单位**发生的；
- 用户结构化输入（如医疗表单中的“年龄”“疾病史”“症状”）若恰好对齐缓存块边界，则可被**逐字段独立验证**。

> **“缓存粒度 = 攻击分辨率”** —— 这一洞见将工业实现的工程约束（块对齐）转化为攻击优势，使得攻击者能像“拼图”一样，**先精确恢复一个字段，再以其为上下文预测下一个字段**，大幅降低搜索空间。

---

#### **(2) 方法论本质：“构造-反馈”闭环优化**

InputSnatch 的“Secret Sauce”在于其**双组件协同机制**：

| 组件 | 功能 | 创新性 |
|------|------|--------|
| **输入构造器**（Input Constructor） | 利用开源领域数据集（如ChatDoctor）学习字段间的语义与统计相关性（如“男性+50岁”常关联“高血压”），生成高概率候选输入；支持多种策略（随机、朴素贝叶斯、细粒度词汇概率、微调LLM）。 | 将**领域知识注入攻击过程**，避免在百万级词表中盲目搜索。 |
| **时间分析器**（Time Analyzer） | 对多次TTFT测量值进行**统计拟合**（如高斯分布建模）并剔除异常点，输出当前候选输入“命中缓存”的置信度，并反馈给构造器以调整后续猜测。 | 将**连续、带噪的时间观测**转化为**离散的缓存状态判断**，实现鲁棒决策。 |

> **数学本质**：该框架将输入窃取问题建模为一个**带约束的黑盒优化问题**：  
> **目标函数**：最小化 TTFT（即最大化缓存命中可能性）  
> **约束条件**：候选输入需符合真实用户输入的分布（通过领域数据学习）  
> **求解策略**：基于反馈的迭代式启发式搜索

---

#### **(3) 实用性与复杂度权衡**

论文明确量化了攻击成本与收益的平衡：
- **效率提升**：相比纯随机猜测（需数万次尝试），基于相关性的构造器（如GaussianNB）仅需约 **1000次API调用** 即可成功；
- **现实可行性**：在典型商业API限制下（5分钟TTL、5000 RPM速率），**精确窃取关键字段**（如疾病名称）；
- **成本瓶颈**：高精度方法（如基于词汇概率的方法）虽成功率更高（62%），但消耗更多token和时间，在严格配额下可能受限。

> 这表明 InputSnatch 不仅是理论攻击，更是**在真实世界约束下可部署的实用威胁**。

---

### 一句话总结
InputSnatch 的根本创新在于：**将大模型侧信道攻击从“模型输出分析”范式，转向“推理基础设施行为分析”范式**。


### 3. 方法实现：架构、算法流程与关键机制

InputSnatch 的攻击框架由 **两大核心组件** 构成：**输入构造器**（Input Constructor） 与 **时间分析器**（Time Analyzer），二者通过**闭环反馈机制**协同工作，形成一个可迭代优化的黑盒攻击系统。其整体架构与执行流程如下：

---

#### **一、系统架构**

整个攻击流程分为 **离线准备阶段** 与 **在线攻击阶段**：

- **离线阶段**：
  - **输入构造器**：从开源领域数据集（如 ChatDoctor）中学习用户输入的字段分布与字段间相关性，构建领域特定的候选生成模型（支持多种策略：随机、高斯朴素贝叶斯、词汇概率模型、微调LLM）。
  - **时间分析器**：对目标 LLM 服务进行探针式采样，建立 **TTFT 与缓存命中块数之间的统计映射关系**（如拟合高斯分布），并设计异常值剔除算法以抑制噪声。

- **在线阶段**：
  1. 攻击者向目标服务发送构造的候选输入；
  2. 精确测量 **首 Token 生成时间**（TTFT）；
  3. 时间分析器判断是否发生缓存命中，并估计命中的块数；
  4. 若命中，则固定当前字段内容，进入下一字段构造；否则，构造器生成新候选；
  5. 重复上述过程，直至完整或部分恢复用户输入。

#### **二、算法流程（以 Prefix Caching + 结构化表单为例）**

假设用户输入为医疗表单，包含字段：`[Age, Gender, Disease History, Symptoms, Duration, Chief Complaints]`。

**Step 1：字段级逐块验证**  
利用 vLLM 等推理引擎的 **块级 KV Cache 管理**（如每块 16 tokens），确保每个字段占据整数个缓存块。这样，当仅前 i 个字段匹配时，TTFT 会显著下降，但第 i+1 个字段不匹配则不会触发额外命中。

**Step 2：迭代式字段重建**
```python
for field_index in range(num_fields):
    while not cache_hit:
        # 基于已成功命中的前缀 + 领域相关性，生成当前字段候选
        candidate = input_constructor.generate(
            prefix=confirmed_prefix,
            target_field=field_index,
            strategy="GaussianNB"  # 或其他策略
        )
        ttft = measure_ttft(candidate)
        hit_blocks = time_analyzer.estimate_hit_blocks(ttft)
        
        if hit_blocks >= expected_blocks_for_current_field:
            confirmed_prefix += candidate[field_index]
            break  # 进入下一字段
        else:
            continue  # 尝试新候选 
```
**Step 3：时间分析器的核心逻辑**

对同一候选输入多次测量 **首 Token 生成时间**（TTFT），得到观测集合：
$$
T = \{t_1, t_2, ..., t_n\}
$$

随后执行以下三步处理：

1. **异常值剔除**：  
   采用 **3σ 原则**（若数据近似正态）或 **IQR**（四分位距法，适用于非高斯分布）剔除因网络抖动、调度延迟等引入的离群点，保留稳定观测。

2. **统计比对**：  
   将清洗后的 TTFT 均值 $\bar{t} = \frac{1}{|T'|}\sum_{t \in T'} t$ 与**离线构建的参考分布库**进行比对。该库包含：
   - “无缓存命中”基线分布（即完全新请求）；
   - “命中 1 块”、“命中 2 块”、…、“命中 K 块”的 TTFT 分布（通过控制前缀长度预先标定）。

3. **状态推断**：  
   输出最可能命中的缓存块数：
   $$
   k^* = \arg\max_k P(k \mid \bar{t})
   $$
   其中 $P(k \mid \bar{t})$ 可通过贝叶斯公式或直接查表估算（假设各 $k$ 对应的 TTFT 服从高斯分布）。

> **关键观察**（原文 Figure 10）：尽管不同 $k$ 对应的 TTFT 分布存在重叠区域（图中红色交叉部分），但由于**每个字段长度通常大于一个缓存块**（如 vLLM 默认块大小为 16 tokens，而“疾病名称”平均 >20 tokens），因此**字段级缓存命中会跨越多个块**，使得 TTFT 下降幅度显著，从而保证**字段判断具有高鲁棒性**，有效避免误差在多字段重建中传播。

### **三、关键机制与“无公式”的数学本质**

尽管论文未显式列出复杂公式，但其方法蕴含清晰的**优化与统计建模思想**：

#### 1. **目标函数隐式定义**
攻击者实质上在求解以下优化问题：
$$
\min_{x \in \mathcal{X}_{\text{domain}}} \quad \text{TTFT}(x)
$$
其中 $\mathcal{X}_{\text{domain}}$ 是由领域知识（如医疗/法律对话数据）约束的合法输入空间。**TTFT 的最小值对应最大缓存命中程度**，即 $x$ 最接近受害者的真实输入。

#### 2. **缓存命中状态的离散化**
虽然 TTFT 是连续变量，但作者通过**分段统计建模**（piecewise statistical modeling）将其映射到离散状态集合 $\{0, 1, 2, ..., K\}$（表示命中的缓存块数）。这一转换将原始回归问题转化为**多分类判别任务**，显著提升在噪声环境下的决策鲁棒性。

#### 3. **搜索空间剪枝**
利用字段间的条件概率关系（例如 $P(\text{Disease} \mid \text{Age}, \text{Gender})$），将原本规模为 $|\mathcal{V}|^L$（词表大小 $|\mathcal{V}|$ 的 $L$ 次方）的指数级搜索空间，压缩至由**高概率路径主导的低维流形**。这使得攻击在有限 API 调用预算下依然可行。

---

### **四、针对 Semantic Caching 的适配**

对于基于语义相似度的缓存系统（如 GPTCache），InputSnatch 调整策略如下：

- **判定简化**：仅需判断是否发生语义命中，即 **TTFT 是否显著低于基线**（甚至趋近于零，因直接返回缓存响应）。
- **构造策略**：输入构造器采用 **层次聚类 + 加权二叉树探索**，在语义嵌入空间中高效生成探测查询，优先测试高频或代表性问题模板。
- **多样性控制**：通过设置**语义相似度阈值**（如 cosine similarity < 0.85）避免重复提交语义相近的查询，提升 token 利用效率。

> 此场景下无需逐字段恢复，而是直接回答：“某类用户问题（如‘高血压怎么治疗？’）是否已被缓存”，适用于 FAQ、客服等固定问答场景。


✅ 总结一句话:在 Semantic Caching 场景下，InputSnatch 不追求“偷看用户说了什么”，而是通过 TTFT 侧信道，高效探测“哪些敏感话题已经被别人问过”——这是一种轻量级但高价值的存在性攻击，特别适合 FAQ、客服、咨询类 LLM 服务。

### **📌 举个真实例子**
假设你在攻击一个在线法律咨询 API，它用了 GPTCache。

你发送：
- ❓ “离婚时孩子归谁？” → TTFT = 12ms → 命中缓存！ → 说明有人问过这个问题。
- ❓ “如何起诉邻居噪音扰民？” → TTFT = 290ms → 未命中。
- ❓ “婚前财产公证流程？” → TTFT = 10ms → 命中！

虽然你没看到具体用户的原始提问（可能是“我和老婆要离婚，5岁儿子跟谁？”），但你已经知道：这个服务中有用户咨询过离婚子女抚养问题


### 4. 论文实验效果分析

该论文通过系统性实验验证了其提出的 **InputSnatch** 攻击框架在两类主流缓存机制（Prefix Caching 与 Semantic Caching）下的有效性、鲁棒性与实用性。实验设计覆盖理想条件与真实世界约束，全面评估了攻击性能。

---

## 一、实验设置

### 1. **攻击场景与目标**
- **场景 1：Prefix Caching（前缀缓存）**  
  - **应用**：静态提示工程的医疗问答系统（模拟“左手医生”平台）  
  - **输入结构**：6 字段表单 — `[年龄, 性别, 疾病史, 症状, 持续时间, 主诉]`  
  - **目标**：精确恢复“疾病史”和“症状”字段（高敏感信息）

- **场景 2：Semantic Caching（语义缓存）**  
  - **应用**：基于 RAG 的法律咨询系统  
  - **目标**：判断特定法律问题是否已被缓存（语义级存在性探测）

### 2. **技术栈与环境**
- **Prefix Caching 平台**：`vLLM 0.6.2`（块大小 = 16 tokens）  
- **Semantic Caching 平台**：`GPTCache` + OpenAI GPT-4o-mini API  
- **模型**：LLaMA-2 70B（Prefix 场景），GPT-4o-mini（Semantic 场景）  
- **硬件**：8×A40 GPU（40GB/卡），128GB 模型内存 + 153GB KV Cache  
- **采样参数**：temperature=0（确定性生成）

### 3. **数据集**
- **医疗领域**：`ChatDoctor` 数据集 → 提取 16,276 条结构化样本，200 条真实 + 200 条 ChatGPT-4 生成样本用于测试  
- **法律领域**：`CrimeKgAssitant` 数据集 → 20 万条 QA 对，覆盖 13 个法律类别，30 条 GPT-4 生成 + 30 条原始样本用于测试

### 4. **现实约束模拟**
- **时间限制**：5 分钟（对齐 OpenAI 缓存 TTL）  
- **速率限制**：5,000 RPM（Requests Per Minute）  
- **内存限制**：最多缓存 250K tokens 的 KV 状态  
- **评估指标**：攻击成功率（ASR）、尝试次数、总 token 消耗、时间消耗

### 5. **输入构造器对比方法**
| 方法 | 描述 |
|------|------|
| **Baseline** | 基于格式化数据集的随机构造 |
| **GaussianNB** | 高斯朴素贝叶斯模型预测字段（Age/Gender 随机，其余 ML） |
| **Prob Vocabulary** | 基于词汇级概率与组合关系的细粒度搜索 |
| **Finetuned LLM** | 微调 LLaMA-3 8B 模型生成候选（temperature=0.99，top-p=0.99） |

## 二、主要结果

### 1. **时间分析器性能**（Table 2 & 3）
- 在 **800-token 输入** 下，仅需 **600 次采样**，即可实现：
  - **86.34%** 的缓存命中块数预测准确率（SR<sub>Block</sub>）
  - **97.25%** 的字段级命中判断准确率（SR<sub>Field</sub>）
- 在 **1600-token 输入** 下，同样 600 采样点：
  - **87.13%** SR<sub>Block</sub>
  - **100%** SR<sub>Field</sub>（因字段间隔 > 块大小，避免误判）

> ✅ 表明：**中等采样开销即可构建高精度时序判别模型**

### 2. **端到端攻击成功率**（Table 4）
#### （1）Prefix Caching（医疗场景）
| 方法 | ASR<sub>disease</sub> (理想) | ASR<sub>symptoms</sub> (理想) | ASR<sub>all</sub> (现实) |
|------|-------------------------------|-------------------------------|--------------------------|
| Baseline | 60.00% | 23.50% | 8.00% |
| GaussianNB | **59.00%** | **27.50%** | **12.50%** |
| Prob Vocabulary | **67.50%** | **53.75%** | 9.50% |
| Finetuned LLM | 54.00% | 18.00% | **0.00%** |

- **关键发现**：
  - **GaussianNB 在现实约束下表现最稳**（12.5% 完整字段恢复）
  - **Prob Vocabulary 精度最高但成本高**（理想下 67.5% 疾病恢复，但现实受限）
  - **微调 LLM 因输出不稳定+高消耗，在现实约束下完全失效**

#### （2）Semantic Caching（法律场景）
- **语义提取成功率**（ASR）按法律类别统计（Table 5）：
  - 最高：**100%**（交通事故、财产纠纷、拆迁安置）
  - 最低：**43.33%**（侵权类）
  - 多数类别 > **90%**
- 表明：在 FAQ 式服务中，**探测“某类问题是否被问过”极为高效**

## 三、消融实验与关键洞察

### 1. **构造策略消融**
- 对比四种构造器，证明：
  - **引入领域相关性**（ML/LLM）显著优于随机猜测（Baseline）
  - **轻量级模型**（GaussianNB）在资源受限时更具实用性
  - **高多样性生成**（如微调 LLM）反而因重复/无效尝试降低效率

### 2. **约束影响分析**
- 从“理想”到“现实”场景：
  - 所有方法 ASR 均下降，但 **GaussianNB 下降幅度最小**
  - **时间与速率限制是主要瓶颈**，而非内存
  - 证明：**攻击在真实 API 环境中依然可行**

### 3. **缓存粒度 vs 攻击分辨率**
- 实验验证：当字段长度 > 缓存块大小（16 tokens）时，
  - 字段级命中判断几乎无误差（SR<sub>Field</sub> ≈ 100%）
  - 即使块级判断有重叠（Figure 10 红区），**不影响整体重建**

### 4. **Semantic Caching 阈值敏感性**
- 实验使用高相似度阈值（0.9）以确保缓存命中质量
- 结果表明：即使在严格匹配下，攻击仍高效 → **说明漏洞普遍存在**

## 四、结论

论文通过严谨的实验设计证明：
1. **InputSnatch 能在真实 API 约束下有效窃取用户输入**；
2. **Prefix Caching 场景可实现字段级精确恢复**（最高 62%）；
3. **Semantic Caching 场景可高效探测敏感问题存在性**（最高 100%）；
4. **轻量级机器学习方法**（如 GaussianNB）。

这些结果不仅验证了攻击的有效性，更**量化了当前 LLM 服务在隐私保护上的严重缺口**，为后续防御研究提供了明确靶标。


### 5. 优点和缺点

### ✅ **优点**

1. **问题定位精准，现实意义强**  
   首次系统性揭示 **工业级 LLM 服务中广泛部署的缓存优化机制**（Prefix/Semantic Caching） 是可被利用的侧信道攻击面，直击当前云上大模型服务的安全盲区。

2. **攻击设计高度实用**  
   - 仅需标准 API 调用权限与时间测量能力，**无需白盒访问、梯度或概率输出**；
   - 兼容真实世界约束（速率限制、TTL、内存配额），证明攻击在**生产环境中可行**。

3. **方法论创新且可迁移**  
   提出“**构造-反馈**”闭环框架，将输入恢复建模为带约束的黑盒优化问题。该范式可扩展至其他推理优化机制（如量化、稀疏注意力）引发的侧信道。

---

### ❌ **缺点与局限**

1. **未在真实商业 API 上端到端验证**  
   Prefix Caching 实验基于本地 vLLM 模拟，Semantic Caching 虽调用 OpenAI API，但**未证明可在 OpenAI 官方 Prefix Caching 机制下完整复现攻击**（如 GPT-4o 的块大小、TTL 策略未知）。

2. **无法关联用户身份**  
   攻击只能恢复“某条输入内容”，但**无法确定该输入来自哪个用户**，限制了部分攻击场景（如定向窃取）的实用性。

3. **依赖结构化输入假设**（Prefix 场景）  
   字段级逐块恢复依赖用户输入具有**固定模板或对齐缓存块边界**。对于自由文本输入（如开放式聊天），攻击效率会显著下降。

4. **语义缓存攻击仅为存在性探测**  
   无法还原原始提问的具体措辞，仅能判断“某类问题是否被问过”，信息粒度较粗。

5. **防御讨论较为初步**  
   虽提出缓存隔离、速率限制等思路，但**缺乏对新型防御机制**（如时序混淆、恒定时间执行）的深入探讨与实验验证。

### 7. 关键术语

| 术语 | 中文 | 解释 |
|------|------|------|
| **Timing Side-Channel Attack** | 时序侧信道攻击 | 通过分析系统执行时间差异推断敏感信息的攻击方法 |
| **Prefix Caching** | 前缀缓存 | 复用具有相同前缀请求的 KV Cache 以加速推理 |
| **Semantic Caching** | 语义缓存 | 对语义相似的请求返回缓存响应，避免重复推理 |
| **TTFT**(Time To First Token) | 首 Token 生成时间 | 从发送请求到收到第一个输出 token 的延迟，是关键观测指标 |
| **KV Cache**(Key-Value Cache) | 键值缓存 | 存储 Attention 计算中 Key/Value 向量的中间结果，用于加速自回归生成 |
| **Block-level Memory Management** | 块级内存管理 | 如 vLLM 将 KV Cache 按固定大小块（如 16 tokens）分配，影响缓存命中粒度 |
| **Attack Success Rate**(ASR) | 攻击成功率 | 成功恢复目标输入（精确或语义）的比例 |
